## 核心结论

William Yun 想建立一个由交易供需决定不同大模型使用额度兑换比例的市场：让用户把闲置、即将到期或暂时不需要的模型额度，换成另一种模型或更晚到期的额度，从而减少重复订阅，并让市场参与模型的相对定价。

**截至 9 月 6 日的材料，项目从方案论证推进到博主自述的原型制作阶段，计划先在测试网上模拟交易；尚无材料证明已经上线或完成真实额度交割。** 早期思路从个人之间交换订阅额度，转向平台中转与多家中转站提供流动性；《实现方案（1）》又指出验证成本、供给来源合规性和官方 API 定价机制等障碍。

新增群聊中，博主明确了近期额度换远期额度、不同模型额度互换两类交易，以及上链、测试网、早期激励和之后寻求投资的推进顺序。他把“用户是否真的愿意卖出闲置 Token”作为早期需求验证重点，并提出后续对接算力方、接入自部署模型及自建可交易 Coding Plan 池子的方向。**新的推进意向没有消除旧问题：他表示早期接受自己所称的“不合规”起步，融资后再转型；具体盈利方法、真实交付规则和合规转型方案仍未说明。**

## 1. 博主到底想交易什么

### 1.1 起点：模型额度的错配

在 A 中，博主由一个用 Token 作德扑筹码的 Codex 插件得到启发，提出暂名 **TokenCoin** 的交易平台。这个灵感不等于他已经验证了该插件的实际额度转移能力。

他的目标使用场景有两类：

- 平时用便宜模型完成普通任务，只在规划或审计时需要高级模型，希望临时交换额度而不必再订阅一家服务。
- 当前订阅额度用不完且即将到期，希望换出去，获得另一模型或更晚到期的使用额度。

因此，他讨论的经济对象可理解为**模型服务的使用额度或交付权益**，不是已经生成的文本本身。这是根据 A、C 的叙述作出的整理性概括；三篇尚未给出统一的交易标的定义。

### 1.2 定价目标：不同模型之间的相对交换比例

博主希望通过订单簿和真实成交形成模型之间的兑换比例。他在 A 的评论中反复强调，模型即使整体降价，仍存在贵与便宜、能力和用途的差异，市场可以对这些差异定价。

面对“必须有稳定币”的说法，他回复可以依靠模型之间直接交换形成价格。另一些回复又把中间 credit、平台代币或稳定币作为备选。因此需要区分：

- **相对明确的目标**：让市场参与不同模型额度的相对定价。
- **尚未统一的结算方案**：直接交换、内部 credit 或稳定币，未在三篇中形成最终选择。

### 1.3 到期时间也是交易条件

他把有有效期的额度类比为期货，设想交换不同到期月份的 Token，并在评论中描述到期后失效的价值特征。

这里的“期货”应保留为博主的类比和设计意向。三篇没有说明完整的标准合约、保证金计算、清算、违约处理或交割规则，不能据此认定已经设计出可运行的期货产品。

## 2. 从公开文章到内部群聊的思想演进

### 2.1 A：从个人额度互换，讨论到平台交付与联合中转站

正文提出“跨模型交换＋到期额度置换＋市场定价”。评论区迫使讨论进一步落到如何交付：

1. **先考虑两条路**：中转平台搭配中间代币，或限额 API 搭配保证金。
2. **认识到个人交割困难**：博主在回复“如何交割”时，认为由平台自己做中转、交易平台内部额度可能更可行；让用户自行交付，最大的障碍是模型掺假。
3. **从单个平台转向多家中转站**：读者提出联合不同中转站后，博主认可这个方向。他随后设想让中转站加入共同协议，以批发渠道和激励吸引供给方。
4. **尝试设计模型验证**：对各中转站声称相同的模型进行相同任务测试，对表现异常者处罚，对表现较好者奖励。
5. **开始遇到规则与信任问题**：评论者提出反代可能违反厂商规则、封号、链上记录无法直接证明模型真假、平台既交易又裁判等问题。

A 中的方案探索不是一套同时成立的最终架构。例如，单一中转站上链、联合多个中转站、使用稳定币和不依赖稳定币，属于不同时间提出的备选或回应。

**配图补充**：A 的 TokenCoin 界面展示了模型与月份、剩余到期天数、买卖深度、订单、成交记录和余额，也出现 USD／USDC 交易对。这能说明他想象的产品形态，但不能证明有真实流动性或成交；界面中的币种和金融字段也不能自动视为正文已经确定的规则。

### 2.2 B：把点子升级为共建计划

博主自述，A 发布后收到技术人士、资金方、交易所及项目从业者关注，并进行了交流；他也自述做过 demo。本次材料无法独立核验这些接触或 demo 的运行程度。

这篇的重要内容是明确列出四个难点：

- Coding Plan 的使用政策。
- 账号额度如何转移。
- 交易交付时如何防止模型造假。
- 如何防止用户在交易中途撤销权限。

当时他仍认为这些问题能够解决，并邀请共同讨论技术路线、合规责任及厂商限制。他计划继续阐述经济性、市场定价、交易系统和模型真假验证，形成白皮书。

**这篇是项目动员和问题框架，不是对上述四项难点的解决证明。** 评论也没有给出额外交付方案：博主留了早期建设群入口，一位读者讨论 Token 的词义，另一位提出洗钱风险。

### 2.3 C：开始排除早期路线，可交易标的仍待确定

虽然标题叫“实现方案（1）”，正文的主要作用是检查前提、否定或削弱旧方案。

#### 路线一：个人订阅额度进入池子

他回顾最初设计：用户把 Coding Plan 通过反代协议接入流动性池；其他人使用后，供给者获得 credit，再交换其他模型池或更远期额度。

随后他认为，每个用户都需要不定期接受模型能力抽检，验证成本过高，因而开始否定 C2C 作为基础交付方式。

#### 路线二：少数中转站作为主要供给方

为减少需要验证的主体，他设想接入几家中转站作为核心流动性提供者，并讨论两种验证方式：

- 由 DPoS 探针节点用户抽检模型能力。
- 自动从不同中转站抽取同名模型，完成同一任务，以表现比较实施奖惩。

他随即意识到：如果中转站加入后既要承担验证与处罚风险，又没有得到足够好处，就未必愿意提供流动性。至此，验证机制和供给方激励并没有同时得到解决。

更大的转折是，他认为依赖 Coding Plan 反代的额度来源存在规则障碍，建立其上的二级市场难以发展。他对中转站来源和合规性的概括是该篇的作者判断，本文不把它扩展成对所有中转服务的事实结论。

#### 路线三：直接交易官方 API 额度

他又考虑官方 API，但在自己的假设下否定了它形成独立浮动市场的可能：

| 他采用的前提 | 他推导的结果 |
| --- | --- |
| 厂商以统一价格持续销售，供给接近无限 | 官方像订单簿上很深的卖单，用户可以直接向官方购买 |
| 按需付费，无须预先囤积 | 用户缺少必须转售闲置额度的动力 |
| 未使用余额不会因闲置而损失 | 不再具备早期“临期额度折价交换”的同样动机 |
| 用户可以绕过二级市场 | 他认为订单会被官方供给吸收，难以形成预想中的价格波动 |

以上是博主的经济性论证及其前提，不是对所有 API 采购合同、额度产品或市场情形的普遍证明。

**C 的终点**：原始订阅额度、联合中转站和官方 API 都暴露出问题；他没有在这篇给出下一种可行交易对象，而是明确留待下一篇。评论中的“更详细设计将发布”也只是一项后续承诺。

### 2.4 D：9 月 6 日群聊——先做原型、验证闲置额度需求，再寻求融资

#### 当前进度与产品范围

13:59—14:03，E（William Yun）表示正在制作原型，准备先上链，在测试网模拟交易，邀请群成员第一批体验，并考虑早期测试激励。他把交易明确分成两类：

- **跨期限交换**：近期 Token 换远期 Token。
- **跨模型交换**：不同模型之间的额度汇率交易。

他把两类交易的机制描述为通过流动性池挂单买卖。但这段群聊仍未说明池子与订单簿如何结合、结算用什么资产，或如何兑现实际模型调用。提到上链与项目发行流程，也不足以确认已经决定发行某种币、采用哪条链或设计了代币经济模型；测试激励的形式和数量同样未说明。

#### 从“公允定价”收敛到一个可测试的用户需求

14:05，博主强调，最核心的需求是用户想卖掉用不完的 Token。他认为提供闲置额度出售入口可能有吸引力，但明确把“是否真的有足够受众”留给早期测试。

**整理判断**：这比早期“改变整个 Token 定价市场”的愿景更具体，提出了一个需要验证的卖方需求。它仍没有回答买方为何持续购买、双边流动性是否足够、用户愿付价格或项目收入来源。14:10，他再次强调由市场决定 Coding Plan 的公允价格，说明定价愿景仍保留。

#### 供给范围扩大：自部署、算力合作与开源模型

对群成员“自部署的可以交易吗”的提问，博主给出肯定答复。14:07，他进一步提出后续两条供给路径：

1. 联系拥有算力的供给方，发布可交易的 Coding Plan。
2. 批发算力、自建 Coding Plan 的可交易流动性池，并先做开源模型交易。

这里的“先做开源模型”出现在他对后续供给路线的说明中，不宜据此断言整个项目的首个测试版本只交易开源模型。材料也没有证明已签订算力合作、取得供给或实现自部署接入。

相较 A 中强调闭源模型相对汇率的定位，D 扩展到了开源和自部署供给；这属于范围扩展及阶段性路线调整，不足以认定放弃了闭源模型目标。

#### 对规则障碍的态度变化

shirley 在 14:03—14:06 连续提出：汇总 Coding Plan 可能变成中转站号池，厂商不允许转售，转售还可能导致模型服务质量下降或账号被封。

博主没有在这段对话中给出消除这些障碍的技术或授权方案。他在 14:06 表示，早期准备从自己所称的“不合规”状态开始，以中转站仍能做大为理由，先形成产品，获得更大融资后再向合规化转型。

**这与 C 存在明显张力**：C 把这类供给的规则问题视为路线的根本障碍；D 则表示愿意在早期接受该障碍，寄望产品和融资支持后续转型。这是推进策略的变化，不能写成“已经解决合规问题”。“其他中转站也不合规”是他的群聊表述，不是本文对相关行业作出的事实判断。

## 4. 从材料能还原出的候选机制

**本节是对博主不同阶段设想的拼接示意，不是他最终确认的架构。**

```text
供给方持有某种模型的服务额度
            ↓
平台接入并记录模型、数量、有效期等交易条件
            ↓
用户挂单交换，或提供调用后获得内部 credit
            ↓
兑换另一种模型／另一有效期的服务额度
            ↓
平台或接入中转站实际提供模型调用

贯穿全程的待解问题：
额度来源与使用权限 → 模型真伪 → 撤权与履约 → 定价与流动性 → 到期处理
```

其中，挂单市场和流动性池／credit 是公开文章中出现过的不同机制；D 又明确提到池子挂单买卖和上链测试。但截至这些材料，仍没有说明其具体组合方式，也没有提供可直接照做的协议或接口规格。

### 比较清楚的目标

- 减少不同模型订阅和使用需求之间的错配。
- 利用闲置额度与剩余期限差异，而不只讨论现金购买。
- 让用户交易参与相对定价。
- 早期重点关注闭源模型的可用服务；D 增加开源、自部署和算力合作供给，仍以额度交易与定价为目标。
- D 把闲置 Token 出售需求作为早期测试重点，计划先做测试网模拟交易。

### 仍未定稿或已被重新审视的部分

- 最终交易标的是什么，以及供给方有何交付、转让权限。
- 个人 C2C 是否可行：C 已因验证成本而明显否定。
- 中转站是否愿意提供流动性，以及验证与奖惩如何运行。
- D 已表达先上链的路线意向；具体链、稳定币或内部 credit 的角色，以及链上与链外交付的关系仍未说明。
- 官方 API 路线是否有满足其目标的具体产品结构：C 的讨论结论是否定当时考虑的直接转售方式。
- 订单撮合、到期、清算、违约和撤权的具体规则。
- 原型和测试网是否实际可用，以及真实供给、买方需求、盈利模式和融资进展。

## 5. 整理判断：怎样准确理解他的思想

以下是基于 A—D 的归纳，不是博主原话。涉及不同时间的判断保留其阶段差异。

**第一，他最稳定的主张是市场参与相对定价，变化最多的是实现载体。** 从 A 到 C，他没有放弃目标，但不断修改谁提供额度、如何验证、怎样交付。

**第二，他把技术问题逐步转化成了市场前提问题。** 早期主要问如何识别假模型，后来意识到，即使识别成功，也还要回答供给方为什么加入、额度是否有权转让、用户为何不直接向厂商购买。

**第三，评论确实推动了论证。** 联合中转站、DPoS 探针、做市、反代规则、裁判公正性等讨论进入了后续思考。但博主采纳一个问题，不等于采纳评论者提出的全部方案。

**第四，截至 C，最准确的项目状态是“有目标、有界面构想、有若干候选机制，正在排除不成立的前提”。** 无法从三篇材料确认已有可持续运行、能够兑现交付的交易市场，也不能用 B 的乐观表述覆盖 C 的自我修正。

**第五，D 将状态更新为“自述正在做原型，准备在测试网验证需求”，而非证明旧障碍已经排除。** 最明显的变化，是他愿意先推进产品、再寄望融资支持合规转型，同时扩展开源与自部署供给。这与 C 的判断需要并列保留，不能把 D 拼接成一条从未有过分歧的完整路线。

**第六，市场需求、收入与融资必须分开。** 卖掉闲置额度是待测需求；群成员考虑投资是条件性意向；二者都不是已经成立的盈利模式。D 中关于运作和收入的提问，仅运作方向得到部分回答。

## 6. 若继续追踪，最值得看的后续问题

这些问题来自 A—D 尚未补齐的环节，用于追踪后续材料，而非额外替博主设计产品：

1. **新标的是什么？** C 对早期路线提出否定意见，D 又把闲置额度交易、自部署和自建 Plan 列入方向；各阶段到底交易什么权益，如何获得交付与转让权限？
2. **供给为何出现？** 卖方为什么愿意折价或换成别的模型额度，接入站点有什么持续收益？
3. **验真如何成立？** 横向能力测试如何区分正常波动与造假，如何处理误判、串通和检测成本？
4. **交付如何保证？** 用户撤权、封号、服务中断和额度到期时，买方权益如何处理？
5. **市场为何有价格发现空间？** 与官方按需购买相比，时间、价格、供应或服务条件的差异在哪里？
6. **交易机制到底是什么？** 已计划上链，但订单簿、流动性池、credit、保证金和期限之间如何对应，模拟成交如何转成真实履约？
7. **需求验证与盈利怎样区分？** 测试网怎样判断真实买卖需求，具体收入来源、成本和收费对象是什么？
8. **后续路线有什么可核验进展？** 原型和网站何时可用，算力合作与自建 Plan 是否落实，有条件的投资意向是否形成实际融资，合规转型靠什么实现？
